Deployment e gestione operativa

Versionamento, test, CI/CD, rilascio, sicurezza, continuità e ownership

Introduzione

L’architettura descrive dove e come collocare R; il deployment definisce come portare quella soluzione in esercizio e mantenerla nel tempo. Il capitolo segue il percorso dalla versione del codice alla produzione, mettendo in evidenza riproducibilità, test, sicurezza, logging, monitoring, rollback, continuità operativa e responsabilità.

Dal codice alla produzione

Un programma che funziona sul PC dello sviluppatore non è automaticamente pronto per essere eseguito in produzione.

Il deployment introduce almeno queste domande:

  1. dove viene eseguito;
  2. con quale versione del codice;
  3. con quali dipendenze;
  4. con quale identità;
  5. a quali dati e sistemi accede;
  6. come viene testato e rilasciato;
  7. come viene monitorato;
  8. come si torna indietro se qualcosa non funziona;
  9. chi interviene in caso di incidente.

Il passaggio alla produzione deve quindi essere trattato come un processo controllato, non come la semplice copia di uno script su un server.

Ambienti: sviluppo, test, produzione

È utile distinguere almeno:

sviluppo → test → produzione

In sviluppo possono essere accettabili modifiche manuali e accesso Internet. In produzione servono invece versioni controllate, configurazione esplicita e procedure ripetibili.

La stessa applicazione può quindi richiedere configurazioni diverse senza cambiare il codice.

Ambiente Obiettivo Caratteristiche
sviluppo costruire e modificare flessibile, modificabile
test verificare una versione controllato, ripetibile
produzione erogare il servizio stabile, monitorato, tracciato

Una modifica dovrebbe attraversare gli ambienti secondo una sequenza definita.

Git e versionamento

Il codice di produzione deve essere riconducibile a una versione precisa.

Per IT questo significa poter rispondere a:

  • quale commit è in esecuzione?
  • quale versione dell’applicazione è stata rilasciata?
  • quali file sono cambiati?
  • chi ha introdotto la modifica?
  • quale versione era precedente?
  • possiamo ricostruire esattamente il rilascio?

Un flusso semplice può essere:

modifica → commit → review → test → release → produzione

Il punto non è imporre un particolare modello di branching. Il requisito importante è la tracciabilità.

Commit, tag e release

Un commit identifica uno stato del repository.

Un tag può identificare una versione rilasciabile, per esempio:

v1.4.0

Una release dovrebbe essere associata almeno a:

  • versione del codice;
  • configurazione prevista;
  • dipendenze;
  • istruzioni di deployment;
  • eventuali migrazioni database;
  • note sulle modifiche;
  • procedura di rollback.

Se non è possibile identificare con precisione ciò che è stato messo in produzione, il rilascio non è realmente tracciato.

Test: che cosa deve essere verificato?

Non tutto deve essere testato allo stesso modo.

Test funzionali

Verificano che l’elaborazione produca il risultato atteso.

input noto → elaborazione → output atteso

Test di integrazione

Verificano l’interazione con componenti esterni:

  • Oracle;
  • filesystem;
  • API;
  • scheduler;
  • servizi aziendali.

Test di regressione

Verificano che una modifica non rompa funzionalità già esistenti.

Test di performance

Sono necessari quando il requisito riguarda:

  • tempo massimo;
  • numero di utenti;
  • dimensione del dataset;
  • consumo di RAM;
  • carico CPU;
  • concorrenza.

Un test di performance deve avere un contesto misurabile. «È veloce» non è un criterio operativo.

Test e dati di produzione

Quando possibile, i test dovrebbero utilizzare dati:

  • sintetici;
  • anonimizzati;
  • minimizzati;
  • rappresentativi del comportamento reale.

L’accesso ai dati di produzione non dovrebbe essere considerato automaticamente necessario solo perché un’applicazione deve essere testata.

CI/CD

La Continuous Integration automatizza almeno una parte dei controlli dopo una modifica al repository.

Un flusso tipico:

push / pull request
        ↓
controlli automatici
        ↓
test
        ↓
build / render
        ↓
artefatto
        ↓
approvazione
        ↓
deploy

La Continuous Delivery/Deployment aggiunge il passaggio controllato verso gli ambienti successivi.

Per una soluzione R, una pipeline può verificare:

  • sintassi e struttura;
  • test automatici;
  • dipendenze;
  • rendering Quarto;
  • costruzione di un’immagine container;
  • presenza dei file richiesti;
  • eventuali controlli di sicurezza;
  • produzione dell’artefatto.

Non è necessario automatizzare tutto dal primo giorno. Anche una pipeline che impedisce di portare in produzione un progetto che non supera i test di base costituisce un miglioramento significativo.

Il ruolo del workflow GitHub Actions

Per questo progetto il workflow di GitHub Actions è un esempio concreto di CI/CD. In un’organizzazione il medesimo processo può essere implementato con GitHub Actions o con un’altra piattaforma aziendale: il principio da governare è la pipeline, non lo specifico prodotto.

Il principio è:

Pull Request → render e controlli
main         → build + pubblicazione

La separazione è importante: una Pull Request deve verificare la modifica senza pubblicarla automaticamente in produzione.

Per un’applicazione R aziendale il medesimo schema può essere adattato:

Git
 ↓
CI
 ↓
test
 ↓
artefatto versionato
 ↓
approvazione
 ↓
deployment

Artefatti

Il deployment non dovrebbe dipendere da una copia manuale e non tracciata dei file.

Un artefatto è il prodotto del processo di build, per esempio:

  • sito HTML;
  • pacchetto applicativo;
  • immagine container;
  • bundle di file;
  • report;
  • eseguibile o servizio configurato.

L’artefatto dovrebbe essere associato alla versione del codice che lo ha prodotto.

Questo rende possibile distinguere:

codice sorgente
     ↓
build
     ↓
artefatto
     ↓
produzione

Configurazione e codice

Un principio importante è separare:

  • codice;
  • configurazione;
  • segreti.

Per esempio, l’indirizzo del database o il percorso di output non dovrebbero essere necessariamente hard-coded nel programma.

Questo facilita il passaggio tra ambienti.

La configurazione dovrebbe inoltre essere versionabile quando non contiene segreti.

Dipendenze R e renv

Una soluzione R dipende non solo dal codice sviluppato internamente, ma anche da:

  • versione di R;
  • pacchetti;
  • versioni dei pacchetti;
  • librerie di sistema;
  • driver;
  • eventuali strumenti esterni.

renv permette di descrivere in modo riproducibile l’ambiente R del progetto.

Il concetto importante per IT è:

il requisito non è soltanto «installare il pacchetto X», ma poter ricostruire l’ambiente necessario per eseguire una specifica versione dell’applicazione.

In produzione bisogna quindi considerare anche:

  • repository dei pacchetti;
  • disponibilità delle versioni richieste;
  • librerie native;
  • compatibilità con il sistema operativo;
  • aggiornamenti di sicurezza;
  • procedura di aggiornamento.

Baseline software e containerizzazione

Quando la riproducibilità dell’ambiente diventa un requisito operativo, renv risolve una parte del problema: descrive le dipendenze R del progetto.

Restano però altri componenti:

  • versione di R;
  • sistema operativo;
  • librerie native;
  • driver;
  • client database;
  • strumenti esterni;
  • configurazione.

Una baseline software può quindi identificare l’insieme delle versioni approvate per una specifica release.

Livello Esempio di evidenza
codice commit/tag Git
R versione
pacchetti R lockfile
OS versione dell’immagine o del sistema
librerie native versioni
driver/client versione
configurazione configurazione dell’ambiente
test suite, dataset e risultato
artefatto identificativo dell’artefatto rilasciato

Containerizzazione

Un container permette di distribuire insieme una parte molto più ampia dell’ambiente software.

Concettualmente:

Immagine container
├── sistema operativo / userland
├── R
├── pacchetti R
├── librerie native
├── applicazione
└── strumenti necessari

Questo può ridurre le differenze tra sviluppo, test e produzione e rendere più prevedibile il deployment.

Il container non rende automaticamente valido il software e non sostituisce i test. Fornisce un artefatto distribuibile che può essere identificato, testato e promosso tra ambienti.

Build, test e release dell’immagine

Un flusso controllato può essere:

flowchart LR
    GIT["Codice versionato"] --> BUILD["Build immagine"]
    BUILD --> TEST["Test automatici"]
    TEST -->|FAIL| DISCARD["Scarto"]
    TEST -->|PASS| IMAGE["Immagine versionata"]
    IMAGE --> REG["Registry"]
    REG --> DEPLOY["Deployment"]
    DEPLOY --> SMOKE["Smoke test"]

L’immagine dovrebbe essere identificabile in modo univoco. Un tag leggibile può essere utile per gli operatori, mentre il digest dell’immagine permette di identificare esattamente l’artefatto distribuito.

L’obiettivo non è dichiarare che il container sia “immutabile” in senso assoluto. L’obiettivo operativo è non modificare manualmente un artefatto già testato: se cambia il contenuto, si costruisce e si testa una nuova versione.

Cosa non risolve Docker

La containerizzazione non risolve automaticamente:

  • la correttezza dell’algoritmo;
  • l’idoneità del metodo scientifico;
  • la qualità dei dati;
  • la gestione dei segreti;
  • la sicurezza dell’immagine;
  • la compatibilità con sistemi esterni;
  • la configurazione dell’ambiente target;
  • il controllo delle modifiche.

Inoltre, un container può dipendere da servizi esterni: database, API, filesystem, autenticazione, certificati o scheduler. La baseline deve quindi identificare anche le dipendenze che rimangono fuori dal container.

Repository dei pacchetti e licenze

Le dipendenze devono essere governabili anche dal punto di vista organizzativo.

Per ogni dipendenza rilevante è utile sapere:

  • nome;
  • versione;
  • origine;
  • licenza;
  • eventuali dipendenze native;
  • modalità di aggiornamento.

Non tutte le dipendenze sono equivalenti dal punto di vista del rischio operativo.

La domanda IT non è soltanto:

«Il pacchetto funziona?»

ma anche:

«Da dove proviene, quale versione usiamo e come gestiamo il suo ciclo di vita?»

Le verifiche legali sulle licenze devono seguire le policy dell’organizzazione.

Sicurezza

Una soluzione R può avere accesso a:

  • database;
  • filesystem;
  • API;
  • dati personali;
  • dati ambientali o scientifici;
  • sistemi interni.

Il principio del least privilege implica che l’applicazione riceva soltanto i permessi necessari.

La richiesta «R deve poter accedere a Oracle» non è quindi sufficiente: bisogna sapere con quale account, verso quali oggetti e per quali operazioni.

Credenziali

Da evitare:

username <- "utente"
password <- "password"

Il problema non è specifico di R: credenziali nel codice possono finire nei repository, nei backup, nei log o nei pacchetti distribuiti.

In produzione le credenziali dovrebbero essere gestite tramite i meccanismi previsti dall’infrastruttura aziendale.

Checklist IT per la gestione sicura delle credenziali

Per una soluzione R in produzione, IT dovrebbe poter verificare almeno:

Controllo Evidenza da verificare
Segreti fuori dal codice ricerca nel repository e nella configurazione versionata; nessuna password, token o chiave hard-coded
Segreti fuori dai log log applicativi e diagnostici non contengono password, token, connection string complete o altri segreti
Identità dedicata l’applicazione usa un account tecnico o un’identità di servizio, non l’account personale dello sviluppatore
Least privilege l’identità dispone solo dei permessi necessari su database, filesystem, API e rete
Recupero a runtime il segreto viene fornito dall’infrastruttura o dal sistema di secret management al momento dell’esecuzione, senza inserirlo nel codice
Permessi sul segreto solo i processi e gli amministratori autorizzati possono leggere o modificare il segreto
Rotazione esiste una procedura per sostituire periodicamente o in caso di compromissione password, token e chiavi
Revoca è possibile disabilitare rapidamente un’identità senza modificare il codice applicativo
Audit accessi e modifiche ai segreti sono registrati secondo le policy aziendali
Separazione ambienti sviluppo, test e produzione non condividono inutilmente le stesse credenziali
Gestione errori un errore di autenticazione non stampa il segreto né una connection string completa
Dipendenze esterne eventuali wallet, certificati, file di configurazione o client database sono inclusi nella baseline e hanno permessi appropriati

Per R, il punto importante è che R non deve diventare il sistema di gestione dei segreti. Il codice dovrebbe ricevere un riferimento o un valore già reso disponibile dall’infrastruttura secondo le modalità approvate dall’organizzazione. La soluzione concreta può usare, per esempio, un secret manager, un credential store del sistema operativo o un’identità gestita; la scelta dipende dall’architettura aziendale.

Domande operative per IT

Prima del rilascio:

  1. Dove viene conservato il segreto?
  2. Chi o quale processo può leggerlo?
  3. L’applicazione usa un’identità dedicata?
  4. Quali permessi ha quell’identità?
  5. Come arriva il segreto al processo R?
  6. È presente in codice, repository, immagine container, file di configurazione o log?
  7. Come viene ruotato?
  8. Come viene revocato?
  9. Come viene registrato l’accesso?
  10. Cosa succede se il segreto scade o viene revocato?
  11. Sviluppo, test e produzione usano identità separate?
  12. La gestione delle credenziali è documentata nella baseline e nella procedura operativa?

Un controllo utile consiste nel verificare non solo il repository, ma l’intera catena:

secret manager / credential store
          ↓
runtime / account di servizio
          ↓
processo R
          ↓
Oracle / API / filesystem

Il principio è minimizzare il numero di componenti che conoscono il segreto e il tempo per cui il segreto rimane disponibile.

Logging

Un job batch dovrebbe almeno permettere di sapere:

  • quando è partito;
  • quando è terminato;
  • quale versione/configurazione ha utilizzato;
  • quanto è durato;
  • se è terminato correttamente;
  • dove si trova l’output;
  • quale errore si è verificato in caso di fallimento.

Un log utile non è necessariamente enorme: deve permettere di ricostruire l’esecuzione.

Error handling

Un errore applicativo non dovrebbe trasformarsi in un fallimento silenzioso.

Un modello semplice:

flowchart TD
    A["Avvio"] --> B["Controlli"]
    B --> C["Elaborazione"]
    C --> D["Successo"]
    C --> E["Errore"]
    E --> F["Log"]
    F --> G["Alert / presa in carico"]

Per un job notturno, «il processo si è fermato» non è una strategia di gestione dell’errore: bisogna sapere che è fallito e perché.

Monitoring

Il monitoraggio deve essere coerente con il tipo di applicazione.

Job batch

Controllare:

  • esecuzione;
  • durata;
  • successo/fallimento;
  • output;
  • CPU/RAM quando rilevanti.

Servizio/API

Controllare:

  • disponibilità;
  • tempi di risposta;
  • errori;
  • numero di richieste;
  • risorse;
  • eventuali saturazioni.

Applicazione Shiny

Aggiungere anche:

  • numero di sessioni;
  • durata delle sessioni;
  • utilizzo di RAM/CPU;
  • errori lato server;
  • comportamento sotto concorrenza.

Rilascio

Un rilascio dovrebbe essere un’operazione identificabile e ripetibile.

Una checklist minima:

  1. codice approvato;
  2. test superati;
  3. dipendenze disponibili;
  4. configurazione verificata;
  5. backup eseguito quando necessario;
  6. versione identificata;
  7. deployment eseguito;
  8. smoke test;
  9. monitoring verificato;
  10. esito registrato.

Smoke test

Dopo il deployment è utile eseguire un controllo minimo che verifichi che il sistema sia effettivamente operativo nell’ambiente target.

Esempi:

  • un endpoint risponde;
  • un job può partire;
  • una connessione al database funziona;
  • un report viene prodotto;
  • una pagina Quarto è raggiungibile.

Lo smoke test non sostituisce i test automatici: verifica che il componente distribuito sia effettivamente utilizzabile nell’ambiente target.

Rollback

Un deployment controllato deve prevedere anche il caso in cui la nuova versione non sia utilizzabile.

Schema:

versione N
   ↓
release N+1
   ↓
smoke test
   ├── OK → mantenere N+1
   └── KO → rollback a N

Il rollback può significare:

  • ripristinare una precedente versione del codice;
  • ridistribuire un precedente artefatto;
  • ripristinare una configurazione;
  • ripristinare dati, quando previsto dalla procedura.

Il rollback diventa più complesso quando il rilascio modifica anche il database. In quel caso bisogna considerare esplicitamente la compatibilità tra versione applicativa e schema dati.

Un rollback non documentato è spesso soltanto un’intenzione.

Backup, RTO e RPO

Per i sistemi che producono o gestiscono dati è utile distinguere:

  • RPO — Recovery Point Objective: quanta perdita di dati è accettabile;
  • RTO — Recovery Time Objective: quanto tempo può trascorrere prima del ripristino.

Esempio:

RPO = 24 h
RTO = 4 h

non significa che il sistema debba essere sempre disponibile. Significa che, secondo i requisiti definiti, l’organizzazione deve poter recuperare i dati con una perdita massima prevista di 24 ore e ripristinare il servizio entro 4 ore.

I valori reali devono essere definiti dal servizio e dalle policy aziendali, non dal linguaggio R.

Continuità operativa

Per una soluzione R in produzione bisogna sapere:

  • dove si trova il codice;
  • dove si trovano gli artefatti;
  • dove sono le configurazioni;
  • dove sono i dati;
  • come vengono gestiti i segreti;
  • come si ricrea l’ambiente;
  • come si ripristina il servizio;
  • chi esegue il ripristino;
  • come viene verificato il ripristino.

Questo porta a una distinzione importante:

backup e disaster recovery non sono sinonimi.

Avere una copia dei dati non dimostra automaticamente di essere in grado di ricostruire l’applicazione.

Modifiche, impatto e nuova baseline

Una modifica a una soluzione in produzione non dovrebbe essere trattata come una semplice installazione o sostituzione di file.

Il percorso minimo è:

modifica proposta
      ↓
analisi dell'impatto
      ↓
test necessari
      ↓
esito dei test
      ↓
approvazione
      ↓
nuova baseline
      ↓
deployment
      ↓
smoke test e monitoring

Esempi di modifiche che possono richiedere una valutazione:

  • aggiornamento di un pacchetto R;
  • nuova versione di R;
  • modifica del codice o dell’algoritmo;
  • aggiornamento del driver Oracle;
  • modifica del sistema operativo;
  • nuova versione dell’immagine container;
  • modifica della configurazione;
  • modifica di un servizio esterno.

L’analisi dell’impatto deve stabilire quali componenti possono cambiare comportamento e quindi quali verifiche sono necessarie. Non tutte le modifiche richiedono gli stessi test.

La registrazione minima della modifica dovrebbe permettere di ricostruire:

Elemento Evidenza
modifica proposta descrizione e motivo
versione precedente baseline/artefatto
impatto valutato componenti interessati
test richiesti elenco
esito risultati e criteri di accettazione
approvazione soggetto/data secondo procedura
nuova baseline versione/artefatto
deployment ambiente e data
verifica post-rilascio smoke test/monitoring

Questo collega change management, verifica del software e baseline.

Lifecycle

Una soluzione può rimanere in produzione per anni.

Occorre quindi prevedere:

sviluppo
   ↓
rilascio
   ↓
esercizio
   ↓
manutenzione
   ↓
aggiornamento
   ↓
ritiro

Durante il ciclo di vita possono cambiare:

  • versione di R;
  • pacchetti;
  • sistema operativo;
  • driver Oracle;
  • certificati;
  • API esterne;
  • requisiti di sicurezza;
  • infrastruttura.

Una soluzione non mantenuta può diventare progressivamente più difficile da supportare anche se il codice non cambia.

Responsabilità

Una soluzione in produzione deve avere responsabilità esplicite.

Area Sviluppatore IT
logica scientifica principale supporto
codice R principale supporto
dipendenze applicative condivisione gestione runtime
OS/server requisiti principale
database requisiti applicativi gestione secondo organizzazione
sicurezza requisiti applicazione policy
performance diagnosi applicativa infrastruttura
monitoring requisiti implementazione operativa
incidenti analisi codice gestione infrastruttura
continuità operativa requisiti applicativi implementazione infrastrutturale

La divisione concreta dipende dall’organizzazione, ma il principio è che ogni componente deve avere un proprietario.

Production readiness

Prima della messa in produzione, la verifica può essere letta come una serie di domande operative.

Codice e versionamento

  • repository versionato;
  • commit identificabile;
  • release/tag;
  • review prevista;
  • changelog o note di rilascio.

Test

  • test funzionali;
  • test di integrazione quando necessari;
  • test di regressione;
  • test di performance quando pertinenti;
  • smoke test post-deployment.

Runtime

  • versione R nota;
  • dipendenze riproducibili;
  • repository dei pacchetti definito;
  • librerie di sistema e driver noti.

Sicurezza

  • account tecnico;
  • least privilege;
  • segreti fuori dal codice;
  • accessi di rete definiti;
  • gestione dei certificati.

Operatività

  • logging;
  • monitoring;
  • alert;
  • backup quando necessario;
  • procedura di rollback;
  • RTO/RPO quando applicabili.

Ownership

  • proprietario applicativo;
  • proprietario infrastrutturale;
  • contatti per gli incidenti;
  • procedura di manutenzione.

La domanda finale non è «funziona?», ma:

possiamo rilasciarlo, monitorarlo, aggiornarlo e ripristinarlo in modo prevedibile?

Le domande fondamentali

Quando un prodotto R passa in produzione:

Dove gira?

PC, VM, container, server?

Come parte?

Manuale, scheduler, servizio?

Con quale versione?

Quale commit, tag o artefatto?

Con quali dipendenze?

Quale R, quali pacchetti, quali driver?

Con quale identità?

Utente personale o account tecnico?

Dove accede?

Database, API, filesystem?

Quando un server dedicato può essere inutile?

Possibili situazioni:

  • il problema è una query Oracle;
  • il codice è fortemente inefficiente;
  • il carico è occasionale;
  • l’elaborazione usa un solo core;
  • il dataset può essere ridotto;
  • il problema è la rete;
  • esiste già un’infrastruttura adeguata;
  • l’applicazione non richiede disponibilità continua.

L’infrastruttura va dimensionata dopo aver compreso il carico e il requisito operativo.

Una pipeline completa

Un esempio realistico può essere rappresentato così:

flowchart LR
    DEV["Sviluppo"] --> GIT["Git"]
    GIT --> PR["Pull Request"]
    PR --> CI["CI: test + controlli"]
    CI --> ART["Artefatto versionato"]
    ART --> APPROVE["Approvazione"]
    APPROVE --> TEST["Ambiente di test"]
    TEST --> SMOKE["Smoke test"]
    SMOKE --> PROD["Produzione"]
    PROD --> MON["Monitoring"]
    MON -->|anomalia| ROLLBACK["Rollback / recovery"]
    ROLLBACK --> PROD

La pipeline non deve necessariamente essere identica per ogni applicazione. Deve però rendere espliciti i passaggi che oggi sono spesso manuali e non tracciati.

Principio operativo

Per IT, la richiesta:

«Ho uno script R, mettetelo sul server»

dovrebbe essere trasformata in una richiesta più precisa:

Quale versione? Quali dipendenze? Quali dati? Quali permessi? Quale frequenza? Quale requisito di servizio? Quali test? Quale monitoring? Quale rollback? Chi è il proprietario?

Questa trasformazione è uno degli obiettivi principali della governance del deployment.
